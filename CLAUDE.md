# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All commands run from `apps/web/` (the only app in this monorepo today):

```bash
npm install
npm run dev            # dev server, http://localhost:3000
npm run build           # production build (also what Jenkins and the Dockerfile run)
npm run lint             # ESLint (flat config via eslint-config-next)
npm test                  # vitest run — all tests, once, no watch
npx vitest run path/to/file.test.ts   # a single test file
npx vitest path/to/file.test.ts        # same file, in watch mode
```

Docker (build context is the repo root, not `apps/web/`):

```bash
docker build -f infra/docker/Dockerfile.web -t goalyst-web:local .
docker compose -f infra/docker/docker-compose.yml up
```

There is no root-level `package.json` — this is intentionally not a workspaces-managed monorepo yet (see Architecture below). Don't run `npm install` from the repo root.

## Architecture

**One app today, structured for more later.** `apps/web` is a Next.js (App Router, TypeScript) app that owns both the frontend and the API routes — there is no separate backend service. `packages/shared` exists for code a second app (the Term 4 Capacitor-wrapped native build) would share with `apps/web`; it's empty until that second consumer exists — don't add speculative abstractions there.

**Every feature traces back to a PRD in `docs/prd/`.** Before implementing or changing a feature, read its PRD — `00-overview.md` indexes all of them and lists which are Built vs. Planned. If you're building something with no corresponding PRD, write the PRD first (see `docs/prd/07-peer-leaderboard.md` for what a deliberately thin/not-yet-ready PRD looks like). `docs/prd/08-non-functional-requirements.md` carries the cross-cutting constraints (per-term cost ceilings, security rules like "the Claude API key and coach prompt logic must stay server-side," privacy/opt-in rules) that apply regardless of which feature you're touching.

**`docs/plan/goalyst-plan.html`** is the original product plan (an HTML artifact, open it in a browser) that the PRDs were derived from. If the plan and a PRD ever disagree, that's a signal one of them is stale — reconcile rather than picking one silently.

**Deployment is staged, not fixed to one target** (`docs/architecture/deployment.md`): a single low-cost VM via Docker Compose for Term 1–2, moving to a managed container platform (ECS Fargate or Cloud Run) at Term 3 when the AI coach introduces real usage-based cost. The CI/CD shape (GitHub → Jenkins → Docker → ghcr.io → deploy) stays constant across terms; `infra/jenkins/Jenkinsfile` implements that pipeline and only its deploy stage changes between terms.

**Repo strategy is monorepo, deliberately** (`docs/architecture/repo-strategy.md`) — one product, one builder, one release cadence. Don't split a piece into its own repo without checking that doc's stated conditions for reconsidering first.

**`apps/web/AGENTS.md` and `apps/web/CLAUDE.md`** are auto-regenerated by Next.js itself on `next dev`/`next build` (not authored) and warn that this Next.js version (16.x) may have API/convention changes from training data — check `apps/web/node_modules/next/dist/docs/` for the current behavior of an API before assuming prior knowledge is accurate, particularly for anything in `app/api/*/route.ts` handlers or config.

**`/api/health`** (`apps/web/src/app/api/health/route.ts`) is load-bearing, not incidental — `infra/docker/docker-compose.yml`'s healthcheck and the Jenkinsfile's post-deploy check both depend on it returning `{"status":"ok"}`. Don't rename or remove it without updating both.

**Cost ceilings are a real constraint, not a suggestion.** `docs/prd/00-overview.md` and `08-non-functional-requirements.md` set explicit per-term $ ceilings (Term 1: $0/mo, Term 2: $0–20/mo, etc.) driven by this being a solo-built, freemium-first product. A dependency or infra change that would blow through the current term's ceiling needs a call-out, not a silent merge.
